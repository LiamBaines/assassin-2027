# ADR 0002: Supabase magic-link auth, verified by Spring

**Status:** accepted

## Decision
- Players log in with a Supabase email magic link. The email carries a `token_hash` link, which works across devices, plus a 6-digit code fallback.
- Next.js calls the Spring API from the server only, passing the Supabase access token as a bearer token.
- Spring is an OAuth2 resource server. It verifies ES256 tokens against Supabase's JWKS (`/auth/v1/.well-known/jwks.json`) and checks issuer `${SUPABASE_URL}/auth/v1` and audience `authenticated`.
- Admins are the emails listed in `APP_ADMIN_EMAILS`. They get `ROLE_ADMIN`, and the web app learns this only from `GET /api/me`.

## Why
- Asymmetric signing keys are Supabase's current default. The API holds no shared secret.
- Server-only calls avoid CORS and keep the API URL private.
- `jws-algorithms: ES256` must be set explicitly, because Spring defaults to RS256 and would reject every token.

## Consequences
- Local dev uses an ES256 key in `supabase/signing_keys.json` (gitignored, created by `scripts/gen-local-signing-key.sh`), so local auth matches production.
- Production needs custom SMTP. Supabase's built-in mailer is rate-limited.
